# 用户与认证模块首期设计方案

版本：v1

日期：2026-11-22

状态：设计稿，尚未实施。

前置调研：`docs/user-auth-research.md`。本文件以随后确认的范围为准，不再将调研报告中的全部选项视为待决策项。

## 1. 目标与已确认范围

**首期实现本机单账号的最小认证闭环，但数据模型与授权逻辑不依赖“永远只有一个用户”。**

已确认：

- 本地用户名密码；通过受控初始化创建唯一账号，不提供公开注册。
- 服务端 Session 与 HttpOnly Cookie；不提供“记住我”。
- 退出当前登录会话；允许同一账号存在多个浏览器登录会话。
- 支持修改密码及本机管理侧重置；改密后其他登录失效。
- 会话与消息必须有明确归属，所有业务访问由后端授权。
- 当前没有历史数据，不做历史归属回填，但仍需结构迁移。
- 主动退出清空临时内容；认证过期时支持同一账号在当前页面运行周期内恢复未提交内容。
- **刷新后的草稿恢复保留为后续需求，首期不实现。**刷新后仍可恢复登录身份，这与恢复草稿是两件事。

不包含：邮箱验证与邮件找回、开放注册、账号管理界面、账号注销删除、团队共享、复杂角色权限、OIDC/SSO、MFA、计费、完整生成任务及流式聊天。

本次只输出设计文档，不修改业务代码，不安装依赖，不执行迁移或测试。

## 2. 架构决策

### 2.1 总体链路

浏览器经 Vite 同源代理访问 `/api/v1`；后续公网改为 HTTPS 下的同源反向代理。前端不直接连接数据库、Redis 或模型服务。

认证链路：浏览器会话 Cookie → FastAPI 身份依赖 → PostgreSQL Session 与用户状态 → 当前用户 → 业务资源授权 → 数据访问。

登录防护：FastAPI → Redis 原子限流 → 受控密码哈希校验 → PostgreSQL 创建 Session。

模块职责：

| 模块 | 职责 |
|---|---|
| 密码与随机凭证组件 | Argon2id 哈希、验证、随机 Session Token、摘要与安全比较 |
| Session 服务 | 创建、验证、到期、撤销和凭证版本检查 |
| 认证服务 | 登录、当前身份、退出、改密 |
| 身份依赖 | 从服务端 Session 确认用户，不能接受请求提交的身份作为依据 |
| 会话业务 | 根据当前用户检查会话及消息访问权 |
| 本机 CLI | 初始化唯一账号、重置密码；不通过 HTTP 暴露 |
| 前端认证状态 | 启动确认、路由访问、失效处理和退出交互 |
| 临时草稿状态 | 仅内存、按用户和资源隔离、同账号重新认证后恢复 |

### 2.2 Session 存 PostgreSQL，Redis 用于登录限流

**首期选择 PostgreSQL 保存 Session。**

理由：已有 SQLAlchemy/Alembic 与 PostgreSQL；会话撤销、改密及用户凭证版本可在同一数据库事务内完成；无需承担数据库与 Redis 之间的认证状态一致性。Redis 已存在，适合原子限流，但不作为身份事实来源。

此选择并不意味着每次请求校验后可永久信任本地缓存。首期每次业务请求都检查服务端会话与用户状态，不缓存可跨请求使用的已认证结果。

未来可以优化会话查询或改变存储实现，但授权依赖的输出和业务资源归属保持稳定。

### 2.3 不引入 JWT、RLS 或通用权限平台

首期不需要 JWT 及续期令牌；不实现 PostgreSQL RLS、团队角色或通用 RBAC。

使用明确的所有者授权：用户只能访问属于自己的会话，消息继承父会话的访问边界。不能用“只部署一个账号”替代授权。

## 3. 数据模型

### 3.1 新增 `users`

| 字段 | 设计 |
|---|---|
| `id` | UUID，稳定业务身份，不使用固定值或用户名作为外键 |
| `username` | 规范化后的用户名，非空、唯一 |
| `password_hash` | Argon2id 编码哈希，包含算法参数与盐，不保存原文 |
| `is_active` | 布尔值，默认启用；认证依赖检查，但首期不提供管理页面 |
| `auth_version` | 非负整数，默认 1；改密或重置时递增，作为凭证失效版本 |
| `created_at`、`updated_at` | 带时区时间 |

`is_active` 是安全校验字段，不代表本期新增完整的禁用管理模块。首期账号资料仅返回 `id`、`username`，不返回密码哈希或内部凭证信息。

“只允许一个账号”由受控创建入口限制，**不在数据库中添加永久只能保存一行的约束**。未来多用户不会要求重建用户表。

### 3.2 新增 `auth_sessions`

| 字段 | 设计 |
|---|---|
| `id` | UUID，服务端会话记录标识，不作为浏览器凭证 |
| `user_id` | 非空用户外键 |
| `token_hash` | 随机 Session Token 的 SHA-256 摘要，唯一索引；不保存原始 Token |
| `auth_version` | 创建时的用户凭证版本快照 |
| `created_at` | 创建时间 |
| `expires_at` | 绝对过期时间，带时区 |
| `revoked_at` | 可空；非空即已撤销 |

索引：`token_hash` 唯一索引、`user_id` 索引、`expires_at` 清理索引。外键可允许用户删除时清理认证会话，但**不据此开放用户删除接口**。

首期不存设备指纹、完整 User-Agent 或原始 IP，不实现设备列表与会话管理页面。

### 3.3 修改 `conversations`

新增非空 `user_id`，外键关联 `users.id`，定义 `ON DELETE RESTRICT`，避免误删用户直接删除全部业务内容。

增加以 `user_id` 开头、衔接 `updated_at`、`created_at`、`id` 的列表查询索引。保留现有排序、200 条上限及 CRUD 能力，不顺带改造分页。

客户端创建或修改会话时不能指定 `user_id`；归属由后端当前身份赋值。会话所有权不可通过当前修改接口转移。

### 3.4 `messages` 继承会话归属

首期不重复添加消息所有者字段，避免消息与会话记录出现两个不一致的归属来源。消息查询和创建前必须通过父会话的所有者检查；保留现有会话删除时消息级联删除。

当前消息接口允许客户端提交 `user`、`assistant`、`system`。首期调整为：

- 浏览器写入仅接受 `role='user'`，缺省也为 `user`。
- `assistant`、`system` 仍可作为数据模型中的内容角色，但未来只能由受信任的后端执行路径写入。
- 公开写入 Schema 禁止额外字段，防止提交伪造所有者等字段。
- 不把消息 `role` 当作账号权限；不为尚未接通的 Agent 消息实现新接口。

未来团队中若区分多位作者，再增加独立作者字段；它与资源所有者并非同一概念。

### 3.5 迁移边界

在现有 `20261120_0002` 之后新增迁移，不改写已存在的迁移历史：创建用户及认证会话表，为业务会话添加非空归属与索引。

用户确认当前无历史数据，因此无需回填。实施时仍应检查目标库：**如果发现已有会话记录，迁移明确失败并提示重新评估，不默认分配用户、不清空数据，也不长期保留无主记录。**

迁移与初始化是两个操作：先迁移结构，再通过 CLI 创建账号。账号初始化不嵌入 Alembic，也不在 API 启动时自动创建。

数据库降级会移除新增归属及认证结构，不应作为上线后的无损回退方案；回退需要停止服务并结合备份评估，不能在可能丢失所有权信息的情况下继续运行旧版无认证接口。

## 4. 密码与初始账号

### 4.1 用户名、密码默认规则

| 项目 | 默认规则 |
|---|---|
| 用户名 | 3–32 位 ASCII 字母、数字、下划线或连字符；首位为字母或数字 |
| 规范化 | 用户名去除首尾空格、统一小写；展示规范化后的用户名 |
| 密码长度 | 15–128 个字符；单因素认证采用较长最小长度 |
| 密码处理 | 不裁剪、不静默截断、不改变大小写，不强制字符类别组合 |
| 表单 | 允许粘贴与密码管理器；密码字段合适的 `autocomplete` |

密码规则对初始化、修改、重置保持一致。登录验证已有密码，不对登录输入重新套用可能随后调整的创建规则，只做合理长度与请求体上限检查。

### 4.2 密码哈希

选用 `argon2-cffi` 提供的 Argon2id；现有后端清单尚无该依赖，实施时固定并验收适用于 Python 3.12 与 Windows 的版本，不在文档中宣称未经验证的最新版本。

初始参数建议：64 MiB 内存、3 次迭代、并行度 1，随机盐至少 16 字节。实际实现需用目标本机测量耗时和内存，调整到可接受延迟，不能为缩短测试耗时降低生产参数。

CPU/内存密集的校验放入有界线程执行，不阻塞异步事件循环；单进程同时进行密码哈希/校验初始限制为 2。用户名不存在时使用同参数的预计算占位哈希校验，结合统一错误降低身份枚举差异。

密码原文只用于本次操作，不能进入数据库、日志、队列、浏览器持久化或命令行参数。

### 4.3 唯一账号初始化

提供本机 CLI 入口，拟定调用名为 `python -m app.cli.auth init-user --username <用户名>`。

- 密码与确认密码通过隐藏输入读取；不支持 `--password`，不提供默认密码。
- 在数据库事务中获取初始化专用 PostgreSQL advisory lock，再检查用户表为空并创建账号。
- 已有账号则拒绝初始化；并发初始化只有一次成功。
- API 没有 `/register`、HTTP 首次安装或公开创建用户入口；不能由“第一个访问网页的人”抢占账号。
- 首期只允许 CLI 创建，且创建路径遵守该锁；唯一用户名约束仍保留。
- 输出操作结果和用户名，不输出密码或 Session Token，不自动登录浏览器。

登录页常驻“首次使用请先运行本机初始化”的提示，不通过 HTTP 探测是否已有账号，不提供用户数量查询，也不据此开放开户。

### 4.4 本机管理侧重置

提供 `python -m app.cli.auth reset-password --username <用户名>`，隐藏读取并确认新密码。

更新密码哈希、递增 `auth_version`、撤销全部用户会话在同一事务中完成。重置后没有保留会话，必须重新登录。执行此工具要求访问本机运行环境和数据库配置，不向 Web 暴露，也不是忘记密码时绕过数据库权限的机制。

## 5. Session 与 Cookie

### 5.1 凭证创建与验证

Session Token 使用密码学随机源生成 32 字节，URL-safe 编码后放入 Cookie。数据库仅存其 SHA-256 摘要；摘要适用于高熵随机 Token，**不能替代密码哈希**。

每次身份校验满足全部条件：

1. Cookie Token 格式合法，摘要对应已有会话。
2. `revoked_at` 为空，`expires_at` 晚于服务端当前时间。
3. 用户存在且 `is_active=True`。
4. Session 的 `auth_version` 等于用户当前版本。

Session 服务返回可信当前用户和当前会话；调用方不能从请求体、查询参数或消息角色补出身份。

### 5.2 默认会话策略

- 绝对有效期 **8 小时**，可通过服务端配置调整。
- 首期不滚动续期、不做空闲超时、不提供刷新令牌接口。
- 刷新页面调用当前身份接口恢复登录，不自动延长有效期。
- 进程重启不会自动撤销 PostgreSQL 中仍有效的会话。
- Cookie 不设置 `Max-Age` 和 `Expires`，属于浏览器会话 Cookie。

“不提供记住我”不等于能可靠检测浏览器关闭。浏览器的会话恢复功能可能恢复会话 Cookie，服务端绝对有效期才是最终上限；首期不承诺关闭浏览器立即撤销服务端会话。

### 5.3 Cookie 属性

| 属性 | 本机开发 | 未来公网 HTTPS |
|---|---|---|
| Session 名称 | `cm_session` | `__Host-cm_session` |
| `HttpOnly` | `True` | `True` |
| `Secure` | 仅本机 HTTP 时为 `False` | 必须为 `True` |
| `SameSite` | `Lax` | 同源方案采用 `Lax` |
| `Path` | `/` | `/`，满足 `__Host-` 约束 |
| `Domain` | 不设置，Host-only | 不设置，Host-only |
| 持久化期限 | 不设置 | 不设置，除非后续明确增加记住登录 |

前端 JavaScript 无法读取 Session Cookie，不把 Session Token 放入响应 JSON、URL 或 `localStorage`。登录成功总是生成新 Token，不沿用客户端原有凭证。

### 5.4 退出与密码变更

- 退出只撤销 Cookie 指向的会话并删除该 Cookie，不撤销其他浏览器会话。
- 同一浏览器的多个标签页通常共享 Cookie，因此属于同一个登录会话，不算多个独立设备会话。
- 修改密码：要求旧密码校验；同一事务中更新密码、递增版本并撤销全部旧会话，再为当前浏览器创建新会话。结果是**其他登录失效，当前浏览器通过新 Cookie 保持登录**。
- 管理侧重置不创建新会话，全部登录失效。
- 过期与撤销在读取时判定，不依赖后台清理是否执行。已过期或已撤销记录可由本机维护命令清理，公网阶段再配置自动清理。

## 6. CSRF、来源与登录防护

### 6.1 同源访问约束

本机推荐固定浏览器入口 `http://localhost:5173`，通过现有 Vite `/api` 代理访问后端。不要混用 `localhost` 与 `127.0.0.1` 期待它们共享 Cookie。

CORS 只允许明确配置的来源，保持 credentials 支持，不能使用来源通配符。针对登录、退出、改密和所有业务写入，验证浏览器 `Origin` 与可信来源完全匹配；禁止 `null` Origin，不通过后缀或字符串前缀匹配判断可信。

API 同时校验可信 Host，防止本机 DNS rebinding。开发代理会改变转发 Host，所以后端允许的本机 Host 与代理配置需一致；不能仅依赖 CORS。

### 6.2 CSRF 方案

采用**签名双提交 Cookie**，同时覆盖登录 CSRF 和已登录写入。

- `GET /auth/csrf` 生成含随机 nonce、签发时间和 HMAC-SHA256 签名的 CSRF Token。
- 签名绑定当前请求携带的格式合法 Session Token 摘要；没有合法 Token 格式时绑定匿名作用域。生成 CSRF 不赋予或证明登录身份。
- Token 写入 Host-only、HttpOnly 的 `cm_csrf` Cookie；公网名称为 `__Host-cm_csrf`。Cookie 的安全属性与 Session Cookie一致，不设持久化期限。
- 同时在 JSON 中返回 `csrf_token` 与 `expires_at`，前端只存内存，写入时放在 `X-CSRF-Token` Header。
- 服务端恒定时间比较 Header 与 Cookie，并检查签名、绑定作用域和有效期，初始有效期 30 分钟。
- 登录或改密创建新 Session 后返回绑定新会话的 CSRF Token；退出清除两个 Cookie。
- `/auth/csrf` 只接受可信 Origin 或可信 Referer 来源，并拒绝明确跨站的 Fetch Metadata；响应禁止缓存。来源策略和代理转发行为必须在真实浏览器中验收。

Origin 校验与 CSRF Token 同时存在；SameSite 只作为额外防线。签名密钥必须来自服务器专用 `auth_secret_key`，不能使用当前占位 `secret_key` 或在每次启动时随机更换。

认证 Cookie 的删除只由显式退出等认证操作执行。普通业务请求或 `/auth/me` 返回 401 时**不附带删除 Cookie 的响应**，避免旧请求的迟到响应清掉刚登录的新 Cookie。

### 6.3 限流与失败策略

使用已有 Redis，通过原子操作维护 TTL 窗口：

- 登录按来源 IP 控制尝试量：初始 10 次/10 分钟。
- 按规范化用户名控制失败量：初始 5 次失败/15 分钟；键使用 HMAC 标识，不保存明文用户名。
- 限制适用于不存在的用户名；成功登录可清理账户失败计数，但不能清理 IP 总量窗口。
- 旧密码校验失败同样受按用户的短期限制。
- 超限返回 429 和 `Retry-After`，不做永久账号锁定。
- Redis 不可用时，登录及需要密码校验的改密返回 503，**不能静默跳过防护**；已有 Session 的普通读取及退出只依赖 PostgreSQL，不强制受 Redis 故障影响。

本机不信任任意 `X-Forwarded-For`。使用真实连接来源；现有开发代理下来源可能统一为本机，但用户名限制仍生效。公网使用真实客户端 IP 时必须先配置可信代理范围，不能直接读取任意转发头。

这些初始阈值面向本机首期，不是公网抗攻击能力的证明。公网需重新评估代理、并发、账户限流造成的拒绝服务风险及边缘防护。

## 7. API 契约

所有新增 API 使用现有 `/api/v1` 前缀。以下路径相对该前缀。

### 7.1 新增接口

| 接口 | 要求与请求 | 成功响应 | 主要失败 |
|---|---|---|---|
| `GET /auth/csrf` | 可信浏览器来源；无需登录 | 200，`csrf_token`、`expires_at`，设置 CSRF Cookie | 403 来源不可信 |
| `POST /auth/login` | CSRF；JSON `username`、`password` | 200，`user`、`session.expires_at`、`csrf_token`、`csrf_expires_at`；设置两种 Cookie | 401 凭证错误；429 限流；503 依赖不可用 |
| `GET /auth/me` | Session | 200，`user`、`session.expires_at` | 401 未登录或会话失效；503 数据库不可用 |
| `POST /auth/logout` | 来源与 CSRF；不要求会话仍有效 | 204，撤销当前会话并删除两种 Cookie | 403 CSRF；503 无法确认撤销 |
| `POST /auth/password` | 有效 Session、CSRF；JSON `current_password`、`new_password` | 200，`user`、`session.expires_at`、`csrf_token`、`csrf_expires_at`；替换 Cookie | 400 旧密码错误；401 会话失效；422 新密码不合规；429、503 |

`user` 只含 `id`、`username`。Session Token 不出现在 JSON。响应带 `Cache-Control: no-store`，现有私有会话与消息响应也禁止共享缓存。

登录页启动时获取 CSRF；认证成功后更新内存 Token。浏览器原 Session 仍有效时重复登录返回 409 `ALREADY_AUTHENTICATED`，前端重新确认当前身份，不创建无意义的重复会话。

退出具备幂等性：会话已过期、已撤销或 Cookie 缺失时，仍在来源与 CSRF 校验通过后返回 204 并清 Cookie。如果带会话凭证但数据库不可达，不能宣称服务端已完成撤销。

### 7.2 现有资源接口保持路径不变

会话列表始终按当前 `user_id` 过滤。按 ID 访问使用“ID＋所有者”条件，找不到或不属于当前用户统一返回 404，避免提供他人资源存在性信息。

消息列表和新增消息先授权父会话；不能只对消息按 `conversation_id` 查询而漏掉所有者。

新建会话由后端设置所有者；现有标题、时间字段和消息响应结构原则上不变，前端无需传所有者。

公共入口：根服务信息、健康探针和就绪探针。开发环境允许默认 API 文档；生产模式关闭默认文档，重新上线文档需要显式授权设计。健康探针不返回账号信息或凭证。

### 7.3 错误契约

新增认证和受影响的会话接口统一使用 `code`、`message`、`details`；`details` 仅含安全字段定位与可展示规则。前端迁移时仍兼容尚未改造接口的字符串 `detail`，不全仓强制改造。

| 状态 | 代表性错误码 | 前端行为 |
|---|---|---|
| 400 | `INVALID_CURRENT_PASSWORD` | 保留登录，显示改密表单错误 |
| 401 | `INVALID_CREDENTIALS` | 登录表单统一“用户名或密码错误”，不触发全局退出 |
| 401 | `AUTH_REQUIRED`、`SESSION_INVALID` | 私有业务进入未认证/重新认证状态 |
| 403 | `CSRF_INVALID`、`ORIGIN_FORBIDDEN` | 不能当成登录过期；重新获取 CSRF 或提示配置问题，不自动重放写入 |
| 404 | `RESOURCE_NOT_FOUND` | 不区分他人资源与不存在资源 |
| 409 | `ALREADY_AUTHENTICATED` | 确认当前身份与路由状态 |
| 422 | `VALIDATION_ERROR` | 安全展示字段错误，不返回密码原文 |
| 429 | `RATE_LIMITED` | 显示等待时间，禁止连续提交 |
| 503 | `AUTH_DEPENDENCY_UNAVAILABLE` | 提示暂时不可用，不能假装是凭证错误或改为匿名运行 |

校验异常转换时移除原始 `input`、请求体及不安全上下文。密码字段即使使用 `SecretStr`，也不能假设框架校验错误天然不会回传原文。

## 8. 关键流程与一致性

### 8.1 登录

1. 验证来源、CSRF、请求长度和格式，进行 Redis 限流。
2. 查找规范化用户名并进行有界 Argon2id 校验；不存在的账号执行占位校验。
3. 校验完成后，在数据库事务中锁定用户并重新检查密码哈希版本、`is_active` 与 `auth_version`，防止与管理侧重置交错产生旧密码的新会话。
4. 创建随机 Token 对应的会话，提交后才返回成功和 Cookie。
5. 登录失败保持统一错误；数据库失败不发送成功 Cookie。

### 8.2 普通业务授权

取得 Session 记录 → 确认用户和会话有效 → 按所有者定位资源 → 执行业务 → 请求内提交。

数据库访问失败返回服务不可用，绝不返回全局资源或默认初始用户。账户版本、归属条件必须来自数据库，而非前端缓存。

### 8.3 退出、改密与并发业务

仅在请求开始做一次身份检查后解除事务约束，会留下“退出已成功但旧请求稍后写入”的窗口。首期需要明确授权与撤销的事务顺序：

- 所有路径统一按“用户 → 认证会话”的顺序加锁，避免锁顺序反转。
- 普通请求对用户与 Session 取得共享行锁并重新检查有效性；写入请求持有到提交，读取请求持有到完成读取。
- 退出对用户取共享锁、对当前 Session 取排他锁，提交撤销后才返回成功。
- 改密、重置从开始使用专用用户排他锁，不先取得共享锁再升级；改密路径还锁定当前会话并重新校验。
- 登录创建会话时锁定用户并检查凭证版本，不能使用重置前的验证结果直接插入。

这样撤销与业务事务有清晰先后关系：已获得有效授权并完成的操作不会被倒撤销；撤销提交后的请求必须失败。**退出不能撤回已经提交的消息，也不能保证网络中已有响应不再到达前端。**迟到响应由前端身份代次隔离。

行锁需在实施时使用 PostgreSQL 验证，包括锁顺序、等待、事务边界和死锁场景；不以 SQLite 模拟宣称验证通过。

### 8.4 修改密码

校验来源、会话、CSRF与失败限流，专用事务锁定用户和当前会话，受控验证旧密码并计算新哈希；更新密码及版本、撤销旧会话、创建当前浏览器新会话，一次提交。

成功响应同时更新 Cookie 和 CSRF。若修改成功但响应丢失，旧会话可能已失效；前端提示结果待确认，使用新密码重新登录，不自动重复改密。

## 9. 前端设计

### 9.1 路由和交互

- 新增 `/login`，不使用业务 `AppLayout`。
- 六个现有业务页面标记需要认证；包括当前主要为占位的页面，保持统一业务边界。
- 应用启动先确认身份，身份未知期间不挂载私有业务页面，避免请求与私有内容闪现。
- 未认证直接访问私有页面进入登录；已认证访问登录页返回安全的站内目标或工作台。
- Header 展示真实用户名，提供退出入口；现有健康状态独立保留。
- `SettingsView` 增加账号/修改密码区域，不升级为管理员控制台。
- 登录页没有注册、邮件找回、记住我入口；提示本机重置方式，不展示密码或默认凭证。

返回地址只接受路由解析后的站内相对路径，拒绝外部 URL、协议相对路径、认证循环路径；不能原样执行用户提供的 `redirect`。

### 9.2 独立认证 Store

新增 `stores/auth.ts`，与当前健康检查 `stores/app.ts` 分离。

关键状态：`unknown`、`authenticated`、`anonymous`、`reauthRequired`、`unavailable`、`loggingOut`、`logoutUncertain`。

数据：当前用户、会话期限、内存 CSRF Token 与期限、身份代次 `authEpoch`，以及被挂起身份的 ID。Store 不保存密码或 Session Token。

启动流程：单次共享的初始化任务调用 `/auth/me`；认证成功后获取 CSRF；401 显示登录，网络错误/503显示重试界面，不能当成未登录。健康检查可独立执行，但不会决定身份状态。

### 9.3 统一请求封装

现有 `api/client.ts` 与 `api/conversations.ts` 各自调用 `fetch`，需要将会话请求接入同一底层客户端，保留各自业务 API 导出，不重写页面全部逻辑。

客户端负责：

- 统一 Base URL、`credentials: 'include'`、错误状态与错误码。
- 私有写入附带 CSRF Header；健康 GET 不依赖认证。
- 识别业务认证失效，区分登录凭证错误与改密表单错误。
- 支持 `AbortController`，私有请求记录发出时的 `authEpoch`。
- 身份代次变化后取消旧请求；即使无法取消或已收到响应，也禁止旧成功、错误和 `finally` 回写新状态。
- 保留聊天现有 `selectionVersion`，它解决资源切换先后顺序，与身份代次不是同一问题。
- 不自动重放新建、发送、改名、删除、改密请求；CSRF 刷新后也由用户明确重新提交。

取消请求不代表服务器没有提交。发送结果不明时，重新认证后刷新消息核对，不自动追加一个新的相同消息。

为避免客户端和 Store 相互 import 形成循环，底层客户端通过注册的认证回调/状态提供器取得 CSRF 与代次；`api/auth.ts` 调用底层客户端，Store 订阅事件，不让客户端直接依赖 Store 实例。

### 9.4 过期、退出与未提交内容

新增内存 `stores/drafts.ts`，仅用于认证过期时的恢复：

- 聊天草稿按用户 ID 与会话 ID 标识。
- 创作草稿保存用户 ID、文章标题和 Tiptap JSON 内容；不保存原消息列表，不声称恢复编辑器撤销栈。
- 内容在认证失效导致页面卸载前快照，重新登录确认同一用户后恢复；需先重新验证目标会话可访问。
- 失效时清掉私有列表、消息、操作弹窗和请求状态，登录界面不显示保留的草稿。
- 若重新登录身份不同，立即丢弃保留内容，即使首期只有一个账号也遵守此规则。
- 主动退出立即清掉草稿与私有视图；普通路由切换不新增自动草稿保存承诺。
- 不使用 `localStorage`、`sessionStorage`、IndexedDB 或服务端草稿表；刷新、关页和浏览器崩溃会丢失草稿，UI 明确提示。

过期恢复仅指未提交内容，不自动恢复尚未完成的发送/删除操作。刷新后的持久化恢复需后续单独设计存储、加密与账号清理边界。

### 9.5 退出失败与多标签页

点击退出后立即隐藏私有内容、递增身份代次、清临时数据并取消请求。收到服务端 204 后才显示“已退出”。

网络失败或 503 时进入 `logoutUncertain`：提示“本地内容已清除，服务端退出尚未确认”，提供重试；由于 HttpOnly Cookie 不能由 JavaScript 清除，不能假装完成服务端撤销。刷新可能恢复仍有效的登录，这一点需要明确提示。

同源标签页使用 `BroadcastChannel` 通知退出和凭证变化；消息不携带 Token、密码或草稿。退出事件清理其他标签页；改密或新登录事件递增代次并重新查询 `/auth/me`，不能仅凭广播认定身份。

首期不依赖浏览器持久化实现跨标签同步。重新获得焦点时可再次确认身份；广播丢失时仍由服务端授权和后续 401兜底。跨标签页并发的登录/退出结果需重新查询确认，不将广播作为认证事实。

## 10. 对现有 Agent 的衔接

已有 `WorkflowContext.user_id` 只是可选传递字段，不构成权限证明。

本次不接通 Agent 到消息 API，也不实现生成任务。保留既有接口，但定义未来调用要求：

## 13. 验证与验收

### 13.1 后端

- 空库迁移、非空旧会话库明确拒绝、并发初始化仅一账号成功。
- 正常/错误密码、用户名大小写规范化、不存在用户统一失败、密码输入不回显。
- Cookie 属性、Session Token 数据库仅存摘要、绝对到期、不因刷新滚动续期。
- 当前会话退出、幂等退出、其他独立会话不受退出影响。
- 改密后旧会话全部失效、当前会话换新、管理侧重置后全部失效。
- 用户 A 不能列出、读取、修改、删除或写消息到用户 B 的会话。测试可直接创建两个用户夹具，不能因产品只允许一个初始化账号而跳过隔离测试。
- 拒绝客户端的 `assistant/system` 消息角色、伪造归属与额外字段。
- 登录与业务写入的来源/CSRF拒绝、过期 Token、绑定作用域变化、跨站请求。
- 限流原子性、429、Redis 不可用时不绕过校验，PostgreSQL 不可用时无匿名回退。
- 登录与改密/重置交错、业务写入与退出交错，以及一致的数据库锁顺序。

认证与会话事务测试使用 PostgreSQL；限流测试覆盖真实 Redis 原子路径。无需执行外部模型请求。

### 13.2 前端与真实浏览器

- 初次打开、直接访问业务路由、刷新身份恢复、后端不可用时不误判未登录。
- 登录凭证错误留在表单；旧密码错误不触发全局退出；CSRF 错误不被误判为会话过期。
- 退出与改密交互；退出失败不宣称成功；同浏览器标签页同步。
- 认证过期后同账号恢复聊天输入、文章标题与正文；不同身份或主动退出不恢复。
- 刷新后草稿确实不恢复，提示与首期边界一致。
- 迟到成功/错误/清理回调不污染新身份，新建或发送结果不明时不自动重放。
- 合法站内返回路径与恶意外部返回路径处理。
- Cookie、Vite 代理、CSRF来源与浏览器缓存行为不能只通过 Vitest/jsdom证明，需真实浏览器验证。

本期不为测试新增完整 RAG、Agent、上传或任务链路。文档测试表是实施后的验收计划，本次未执行，不宣称通过。

## 14. 建议实施顺序

1. **身份与归属基础**：结构迁移、密码组件、唯一账号初始化/重置、用户及 Session模型。
2. **后端认证闭环**：来源/CSRF、限流、登录/当前身份/退出/改密，完成一致性与失败语义。
3. **业务数据保护**：会话归属过滤、所有对象授权、消息角色与输入边界，验证双用户隔离。
4. **前端登录体验**：统一客户端、启动和路由身份、Header、改密及安全错误处理。
5. **失效与退出体验**：请求代次、临时草稿、多标签通知与退出结果不确定处理。
6. **本机交付验收**：运行配置、操作说明、真实数据库/浏览器验证和回归。

每个阶段是可验证的功能单元。后端未完成资源隔离前，不将前端登录页面视为可交付安全闭环；整个过程不开放公网。

## 15. 公网演进边界

可以延续：UUID 用户身份、会话与消息归属、服务端 Session、对象级授权、统一错误、前端身份状态和凭证版本撤销。公网不要求自动切换 JWT。

上线前必须另行补齐或重新评审：

- HTTPS 同源反代、可信代理/IP、基础设施访问限制、秘密管理与备份恢复。
- 开户、验证、恢复通道、账号生命周期及滥用处置。
- 多实例限流、密码校验总并发、会话清理、监控与安全事件响应。
- 模型调用额度、用户级费用责任与外发数据范围；当前登录限流不能控制模型成本。
- 团队共享需要新的授权模型，不能直接取消个人归属检查。
- 接入 OIDC时将外部身份映射到稳定本地用户 ID，不从相似用户名自动合并账号。
- 草稿跨刷新恢复需要独立持久化设计，不能直接把全部私有内容塞进 `localStorage`。

**本方案消除未来演进中明显的身份与数据结构返工，但不承诺“改一个部署地址即可成为公网服务”。**

## 16. 设计结论

首期以“本地用户名密码＋PostgreSQL Session＋安全 Cookie/CSRF＋所有者授权”为主线；Redis承担登录防护，本机 CLI承担开户与恢复。前端补齐身份状态、可靠退出、请求隔离和不跨刷新的临时内容恢复。

没有新的外部认证服务或额外产品决策阻塞。8 小时会话、30 分钟 CSRF和限流参数是明确的技术默认值，可在实施验收中调整，不改变已经确认的产品范围。

本方案只设计必要闭环，不提前实现团队、公开注册、第三方身份、计费或生成平台。
